# Life OS — Операции и продакшен (Фаза 5)

> Что уже реализовано и что запланировано. Хостинг на старте — локальный, поэтому часть пунктов
> (registry, оркестратор, алертинг) описана как план и включается при появлении цели развёртывания.

## 1. CI/CD и гейты безопасности (реализовано)

GitHub Actions:

- **`ci.yml`** — на каждый push/PR в `main`:
  - `quality`: build → lint (ESLint) → format:check (Prettier) → typecheck → test → validate:content.
  - `sca`: `pnpm audit --prod --audit-level=high` — блокирует при high/critical в prod-зависимостях.
  - `secrets`: gitleaks — сканирование секретов в истории и диффе.
- **`codeql.yml`** — SAST (CodeQL, `security-and-quality`) на push/PR + еженедельно.
- **`deploy.yml`** — сборка Docker-образов API и web (валидация деплой-артефактов; push в registry — по мере появления цели).

Все гейты — блокирующие (падение job = красный статус, мешает мержу при branch protection).
Локально те же команды: `pnpm lint && pnpm format:check && pnpm typecheck && pnpm test && pnpm validate:content && pnpm audit --prod --audit-level=high`.

## 2. Окружения

| Окружение             | Как                                                                    | БД                      |
| --------------------- | ---------------------------------------------------------------------- | ----------------------- |
| **dev (zero-config)** | `pnpm --filter @life-os/api dev` + `@life-os/web dev`                  | in-memory               |
| **dev + Postgres**    | `docker compose -f infra/docker/docker-compose.yml up -d` + `.env`     | Postgres 17 (порт 5433) |
| **staging/prod**      | `docker compose -f infra/docker/docker-compose.prod.yml up -d --build` | Postgres в сети compose |

Секреты — только через переменные окружения/секрет-менеджер, не в репозитории (`.env` в `.gitignore`,
`POSTGRES_PASSWORD` через env). Пароль БД в prod-compose берётся из `POSTGRES_PASSWORD`.

## 3. Миграции БД без даунтайма

- Инструмент: **Drizzle** (`pnpm --filter @life-os/api db:generate` → SQL в `apps/api/drizzle`, `db:migrate` применяет).
- Стратегия **expand/contract** (backward-compatible): сначала аддитивная миграция (новые
  колонки/таблицы nullable), деплой кода, работающего со старой и новой схемой, затем отдельным
  релизом — «contract» (удаление старого). Миграции применяются **до** старта новой версии приложения.
- Первичные ключи — UUIDv7, sync-метаданные у каждой записи (совместимость с offline-sync, ADR 0003).

## 4. Логирование, мониторинг, алертинг

- **Health-check**: `GET /api/v1/health` (реализовано) — для проб готовности/живости оркестратора.
- **Структурированные логи без PII** (реализовано): pino + pino-http — JSON-логи запросов (метод/путь/
  статус/время), тела запросов НЕ логируются, чувствительные заголовки (authorization/cookie/x-dev-user)
  вырезаются (`src/common/logger.ts`).
- **Экспорт и удаление данных** (реализовано): `GET /api/v1/account/export` (переносимость),
  `DELETE /api/v1/account` (право на забвение — стирает объекты, решения, членства, настройки ИИ).
- **Алертинг** (план): аномалии из требований безопасности — множественные неудачные входы, массовый
  экспорт данных, аномальный доступ; источник — аудит-лог Household + метрики ошибок/латентности.

## 5. Резервное копирование и восстановление (DR)

- **Backup** (план): регулярный `pg_dump`/`pg_basebackup` + WAL-архив; шифрование бэкапов; хранение
  вне основного хоста.
- **Restore-тест** (принцип): проверяется **реальное восстановление** в изолированное окружение по
  расписанию, а не только наличие бэкапа. Цели RPO/RTO фиксируются до публичного запуска.

## 6. Нагрузочное тестирование (план)

Перед публичным запуском — сценарии k6 на критичные пути (создание/чтение объектов, синхронизация,
права доступа), с целевыми p95-латентностью и порогом ошибок как гейтом.

## 7. Реакция на инциденты (кратко)

Обнаружение → изоляция (revoke сессий/доступа, аудит-лог неизменяем) → оценка → уведомление →
устранение → разбор. Возможность быстро отозвать доступ заложена в модель (membership/session).

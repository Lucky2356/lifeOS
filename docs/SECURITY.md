# Life OS — Безопасность и Threat Model

> Безопасность — сквозное требование на всех фазах, не «фаза в конце». Threat model составлен до
> кодирования критичных модулей (Life Ledger, Household OS), как требует промт.

## 1. Что защищаем (активы)

- Персональные документы и их сканы/фото (удостоверения личности).
- Медицинские записи (приёмы, рецепты, история).
- Финансовые данные (обязательства, расходы, доли).
- **Данные детей** в Household OS (повышенная чувствительность).
- Учётные данные и сессии, ключи шифрования, аудит-логи.

## 2. Модель угроз (STRIDE, кратко)

| Угроза                     | Пример вектора                        | Мера                                                                                                |
| -------------------------- | ------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **Spoofing**               | Кража токена/сессии, фишинг           | MFA (TOTP/passkey), короткоживущие токены + ротация, привязка к устройству, secure/httpOnly cookies |
| **Tampering**              | Подмена данных на клиенте/в транзите  | TLS everywhere, подпись/версионирование записей (HLC, version), серверная валидация всех мутаций    |
| **Repudiation**            | Отрицание действия в общем доме       | Неизменяемый audit-log действий над общими ресурсами                                                |
| **Information disclosure** | Доступ к чужим данным, утечка в логах | Row-Level Security в БД + API-проверки, шифрование at-rest, логи без PII                            |
| **Denial of service**      | Брутфорс, флуд эндпоинтов             | Rate limiting, экспоненциальные задержки, защита от enumeration                                     |
| **Elevation of privilege** | Ребёнок/гость получает лишние права   | Наименьшие привилегии по умолчанию, проверка прав на каждый объект, авто-отзыв гостя                |

**Кто атакующий:** внешний аноним; авторизованный, но чужой пользователь (multi-tenant isolation);
участник дома с ограниченной ролью (child/guest), пытающийся расширить доступ; вредоносный загружаемый файл.

## 3. Аутентификация и доступ

- Argon2id для паролей; обязательная поддержка MFA (TOTP + passkeys/WebAuthn).
- Сессии: короткий access-токен + ротируемый refresh, хранение хэшей, список сессий/устройств, revoke.
- Авторизация row-level (RLS в PostgreSQL) + проверки в API. Отдельные урезанные права child/guest.

## 4. Данные

- **In transit:** TLS everywhere.
- **At rest:** шифрование БД + **дополнительное поле-уровневое** шифрование чувствительных категорий
  (медицина, документы, удостоверения) — приложением, перед записью.
- **Управление ключами:** отдельно от данных (KMS/secret manager). Никаких секретов в коде/репозитории
  (`.env` вне git, secret-scanning в CI). Ключи ротируемы; `encryption_key_id` хранится с записью/файлом.
- **Совместимость с sync:** шифрование поле-уровневое, чтобы конфликт-резолюция работала по метаданным,
  а не по расшифрованному содержимому.
- **Права пользователя:** экспорт всех данных, полное удаление аккаунта («право на забвение»),
  журнал доступа к данным в доме.

## 5. Загружаемые файлы (сканы/фото)

- Валидация типа (allow-list) и размера; проверка реального содержимого (magic bytes), не только расширения.
- Антивирус/скан на вредоносный контент: `scan_status` (pending→clean/blocked); до `clean` файл не отдаётся.
  (В MVP — интерфейс скана + заглушка-провайдер; продовый провайдер подключается позже.)
- Хранение изолировано от исполняемого кода (объектное хранилище, не веб-корень), доступ только через
  авторизованную выдачу с расшифровкой. Никакого исполнения загруженного контента.

## 6. Защита кода/инфраструктуры (OWASP Top 10)

- Broken access control → RLS + row-level проверки + тесты доступа (child/guest не видят лишнего).
- Injection → параметризованные запросы (ORM), валидация входа (Zod) на границе.
- XSS → экранирование по умолчанию (React), CSP; никакого `dangerouslySetInnerHTML` без санитайза.
- CSRF → SameSite-cookies + анти-CSRF для state-changing запросов, где применимо.
- SSRF → allow-list исходящих запросов (важно для AI-провайдера и загрузки по URL).
- Небезопасная десериализация → строгие схемы, без произвольного eval/десериализации.
- Rate limiting и защита от enumeration на auth и чувствительных эндпоинтах.

## 7. CI-гейты безопасности (блокируют мердж при критичных находках)

- **SAST** (статический анализ) + строгий линт/типизация.
- **SCA** — сканирование зависимостей на уязвимости.
- **Secret scanning** — блок при найденных секретах.
- Тест «все критичные пути зелёные при выключенном ИИ» (принцип ADR 0005).
- Тесты изоляции доступа (multi-tenant, роли).

## 8. Наблюдаемость и реакция на инциденты

- Структурированные логи **без PII**; алертинг на подозрительное: множественные неудачные входы,
  аномальный доступ, массовый экспорт данных.
- Аудит-логи неизменяемы; возможность быстро отозвать доступ/сессии.
- Краткий incident response: обнаружение → изоляция (revoke) → оценка → уведомление → устранение → разбор.

## 9. Явное ограничение

Проект **не** содержит и не описывает вредоносный код (malware/эксплойты) даже «для теста защиты».
Защита строится на признанных практиках, статических анализаторах и мерах выше.

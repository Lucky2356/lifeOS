# ADR 0001 — Технологический стек

- Статус: **Принято** (утверждено заказчиком, Фаза 1)
- Дата: 2026-07-04

## Контекст

Требуется: web-PWA первым клиентом, offline-first + near-realtime синхронизация, общий бэкенд и
доменная модель для будущих desktop/mobile, личный масштаб (до 100 пользователей), сильная
безопасность, долгосрочная поддерживаемость. Хостинг на старте — локальный.

## Рассмотренные варианты

- **A. TypeScript-монорепо + PostgreSQL + local-first движок** (React PWA, NestJS, Drizzle, Electric/PowerSync).
- **B. Supabase (BaaS) + PowerSync** — быстрее к MVP, RLS/Auth/Storage из коробки, self-host возможен.
- **C. Elixir/Phoenix + TS-фронт** — сильный realtime, но два языка и нет общего домена с клиентами.

## Решение

Выбран **Вариант A**.

## Обоснование

- Один язык (TypeScript) на клиенте, сервере и в общем доменном пакете → максимум переиспользования
  кода между web / будущими desktop (Tauri) и mobile (Expo/React Native).
- Строгая типизация end-to-end (TS strict + Zod-схемы, общие для клиента и сервера).
- Синхронизация — самая рискованная часть — решается зрелым local-first движком, а не самописным CRDT.
- Полный контроль над бэкенд-логикой и данными (важно для приватности, хостинг локальный).
- PostgreSQL Row-Level Security ложится на требование row-level авторизации Household OS.

## Последствия

- Нужен аккуратный выбор конкретного sync-движка — вынесен в отдельный ADR 0003, требует раннего спайка.
- Монорепо (pnpm + Turborepo) с самого начала — небольшая стартовая сложность окупается переиспользованием.

## Отвергнуто

- **B** — отличный вариант для скорости, но вводит платформенную привязку и меньше контроля над
  серверной логикой; при локальном хостинге преимущество «готового BaaS» частично теряется. Оставлен
  как запасной путь при желании ускорить MVP.
- **C** — два языка убивают ключевое преимущество общего домена для трёх клиентов.

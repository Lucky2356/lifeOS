# ADR 0002 — Стиль архитектуры: модульный монолит

- Статус: **Принято**
- Дата: 2026-07-04

## Контекст

5 модулей (Life Ledger, Household OS, Decision Companion, Bureaucracy Autopilot, Crisis Navigator) +
AI-слой + content-pack-движок. Требование: чёткие границы модулей (изменение одного не требует правок
в остальных). Масштаб на старте — личный (до 100 пользователей), команда небольшая.

## Решение

**Модульный монолит** (modular monolith): единое разворачиваемое приложение с внутренними модулями,
у каждого — явная граница (собственные сервисы, свои таблицы/схема, публичный контракт-порт).
Микросервисы **не** вводим на старте.

## Обоснование

- Микросервисы на масштабе до 100 пользователей дают распределённую сложность (сеть, консистентность,
  деплой N сервисов) без выигрыша — антипаттерн для этого этапа.
- Модульные границы внутри монолита дают 90% преимуществ изоляции при 10% операционной цены.
- Общая доменная модель без дублирования сущностей проще держать консистентной в одном процессе.
- Границы спроектированы так, чтобы при реальной необходимости модуль можно было вынести в сервис
  (общение между модулями только через публичные порты/интерфейсы, не через прямой доступ к чужим таблицам).

## Правила границ

- Каждый модуль — отдельный пакет/каталог с `public` API (порт) и приватной реализацией.
- Кросс-модульные вызовы — только через порты, никакого прямого импорта внутренних сервисов/репозиториев.
- Каждый модуль владеет своей группой таблиц (префикс схемы). Чужие данные — только через порт-владелец.
- AI-слой и content-pack-движок — тоже модули с портами; core не зависит от них (зависимость инвертирована).

## Последствия

- Нужен дисциплинирующий инструмент границ (ESLint boundaries / dependency-cruiser) как CI-гейт.
- Единый деплой — проще для локального хостинга и MVP.

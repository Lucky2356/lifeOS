# ADR 0003 — Offline-first синхронизация и разрешение конфликтов

- Статус: **Принято** (с ранним спайком для подтверждения движка)
- Дата: 2026-07-04

## Контекст
Приложение должно быть полностью пригодно офлайн (просмотр и редактирование Ledger, отметка задач,
просмотр чек-листов) с последующей near-realtime синхронизацией и предсказуемым разрешением конфликтов
между устройствами одного пользователя/семьи.

## Рассмотренные подходы
- **Самописный CRDT/OT** — максимум контроля, максимум риска и времени. Отвергнут для MVP.
- **Read-path sync + write-through API** (ElectricSQL v1 «shapes»): сервер — источник истины; клиент
  держит локальную SQLite-реплику для чтения офлайн; записи идут через наш API с очередью офлайн-мутаций.
- **Bidirectional local-first** (PowerSync): локальная SQLite + upload-очередь, сервер применяет мутации,
  конфликты разрешаются на сервере детерминированными правилами.

## Решение
Гибрид с **чёткой моделью владения данными и детерминированным разрешением конфликтов**:

1. **Локальное хранилище клиента** — SQLite (через local-first движок), приложение читает/пишет локально,
   работает офлайн без деградации.
2. **Движок синхронизации** — на старте **PowerSync** (зрелый write-path для offline-first) как основной
   кандидат; **ElectricSQL** — запасной. Финал подтверждается спайком в начале Фазы 3.
3. **Разрешение конфликтов** — на уровне полей, детерминированно:
   - Для большинства полей — **Last-Writer-Wins по Hybrid Logical Clock (HLC)**, а не по wall-clock.
   - Для «наборов» (теги, участники, вложения) — **add-wins set** (CRDT-семантика множеств).
   - Для критичных полей (статусы задач, финансовые суммы) — конфликт **не** тихо разрешается, а
     помечается и показывается пользователю на разрешение (важно для доверия к данным).
4. **Модель данных, дружественная к sync:** у каждой записи — `id` (UUIDv7), `updated_at`,
   `hlc` (логические часы), `deleted_at` (soft-delete / tombstone), `version`. Никаких серверных
   автоинкрементов как первичных ключей (конфликтуют при офлайн-создании).

## Обоснование
- Готовый движок снимает самый рискованный кусок с самописной реализации.
- HLC вместо wall-clock устраняет проблему рассинхрона часов устройств.
- Явное разрешение конфликтов для критичных полей — требование доверия (данные о деньгах/здоровье).

## Последствия
- Первичные ключи — UUIDv7 везде; проектирование таблиц уже с полями sync-метаданных.
- Нужен ранний спайк (Фаза 3, срез Life Ledger) для подтверждения выбора движка на реальном сценарии
  «создать объект офлайн на двух устройствах → синхронизация → конфликт».
- Шифрование чувствительных полей должно быть совместимо с sync (см. ADR по безопасности / SECURITY.md).

# ADR 0004 — Архитектура Content Packs

- Статус: **Принято**
- Дата: 2026-07-04

## Контекст

Плейбуки Crisis Navigator, гиды Bureaucracy Autopilot и юридические нормы регионально-зависимы и
локализуемы. Ядро (модель данных, API, UI) должно быть регионально-независимым: второй/третий регион
добавляется **без изменения кода ядра**. На старте — один пак: регион РФ, языки RU + EN.

## Решение

**Content Pack** — версионируемый, подключаемый, локализуемый набор данных (не код):

- **Идентификация:** `pack_id` (напр. `ru`), `version` (semver), поддерживаемые `locales` (`ru`, `en`).
- **Формат:** декларативные данные (JSON/YAML) по строгой **схеме контента** (Zod/JSON-Schema),
  валидируемой в CI. Контент отделён от строк локализации (ключи → переводы по локали).
- **Содержимое пака:**
  - Плейбуки (Crisis Navigator): шаги, условия, требуемые типы документов, ссылки на инстанции.
  - Гиды (Bureaucracy Autopilot): пошаговые процессы, дедлайны, статусы, требуемые документы.
  - Справочники: типы документов региона, юридические сроки, категории.
- **Привязка к данным пользователя — по абстрактным типам**, а не по конкретике: шаг ссылается на
  `document_type: "passport"` (тип из справочника пака), а движок сопоставляет с реальными объектами
  Life Ledger пользователя. Ядро не знает про «российский паспорт» — знает пак.
- **Версионирование и обновление:** паки версионируются и обновляются **независимо от релиза приложения**
  (загрузка/обновление данных пака без пересборки клиента). Пользовательский прогресс по плейбуку хранит
  ссылку на версию пака; миграция прогресса при обновлении пака — по правилам совместимости.
- **Локализация:** i18n-движок приложения (интерфейс) и локали контент-пака — единый механизм ключей,
  но раздельные пространства имён (UI-строки vs контент региона).

## Обоснование

- Данные-вместо-кода = добавление региона не трогает ядро (проверяемо на RU/EN как критерий успеха MVP).
- Абстрактные типы документов разрывают связь ядра с конкретным регионом.
- Независимое обновление паков позволяет править контент (изменился закон) без релиза приложений.

## Последствия

- Нужна строгая схема контента + валидатор в CI (битый пак не проходит мердж).
- Нужен реестр паков и механизм их доставки/версионирования (в MVP — локально из репозитория/каталога).
- Прогресс пользователя по плейбукам/гидам хранит `pack_id` + `pack_version`.

# ADR 0006 — Приложение без сервера: только устройство

- Статус: **Принято**
- Дата: 2026-08-19
- Заменяет: [0002 (модульный монолит)](0002-modular-monolith.md),
  [0003 (offline-first синхронизация)](0003-offline-sync.md),
  [0005 (ИИ как опциональный слой)](0005-ai-optional-layer.md)

## Контекст

Life OS была построена как клиент-серверный продукт: NestJS API, PostgreSQL, Docker, TLS через Caddy,
аккаунты с argon2/TOTP/passkeys, вложения на серверном диске, offline-first клиент с очередью мутаций.
Всё это работало, но требовало постоянной эксплуатации: сервер, домен, сертификаты, бэкапы базы,
SMTP, обновления образов, ротация ключей.

Продукт при этом личный: один человек (и его семья) ведёт свои документы, дела и решения. Ценность
сервера сводилась к трём вещам — синхронизация между устройствами, совместный семейный доступ и
проксирование ИИ-запросов. Каждая из них платится постоянной эксплуатационной нагрузкой и тем, что
данные о документах, здоровье и деньгах лежат на машине, которую надо защищать.

## Решение

Сервера нет. Приложение работает только на устройстве:

1. **Хранилище — IndexedDB** на устройстве. Это единственный источник правды; сети нет вообще.
   Вложения (сканы, PDF) хранятся там же, байтами.
2. **Аккаунтов нет.** Ни регистрации, ни пароля, ни MFA/passkeys. Приложение открывается сразу;
   разграничение доступа — задача учётной записи операционной системы.
3. **Одна кодовая база — две оболочки.** React-приложение (`apps/app`) упаковывается в Android APK
   (Capacitor) и Windows-установщик (Tauri). Предметная логика остаётся в `packages/domain` и
   исполняется на клиенте — там она была и раньше.
4. **Перенос данных — экспорт/импорт файлом.** Один JSON со всеми записями и вложениями в base64.
   Это же единственный способ резервного копирования.
5. **Совместного доступа нет.** Модуль «Дом» становится личным: люди — справочник для назначения
   задач, задачи — общий список. Приглашений, ролевого доступа и журнала аудита нет.
6. **ИИ-слоя нет.** Ключи провайдеров жили на сервере и проксировать их больше негде; класть чужой
   API-ключ на устройство и звать провайдера напрямую означало бы, что приложение перестаёт быть
   офлайновым.

## Обоснование

- Данные не покидают устройство не по обещанию в политике, а потому что их некуда отправить.
- Эксплуатации нет: нечего обновлять, нечего ломать, нечего терять при отключении сервера.
- Убирается весь класс серверных рисков (RLS, ротация ключей, TLS, CSRF, утечка через API).
- Предметная логика уже была на клиенте — удаляется транспорт и хранение, а не правила.

## Последствия

- Единственная копия данных — на устройстве. Экспорт из настроек становится обязательной частью
  продукта, а не удобством. В Android отключён системный авто-бэкап (`allowBackup=false`), чтобы
  данные не уезжали в облако вопреки обещанию.
- Вложения на устройстве **не шифруются**. Без пароля пользователя ключ пришлось бы держать рядом с
  данными — это защита только на вид. Реальная защита — песочница приложения и шифрование диска ОС.
- Данные привязаны к origin оболочки: `appId`/`androidScheme` (Capacitor) и `identifier` (Tauri)
  заморожены — их изменение делает существующую базу недоступной.
- `version` и `deletedAt` в схемах остаются, но теперь работают на импорт резервных копий, а не на
  синхронизацию. Заглушка HLC удалена.
- Напоминания о сроках: на Android планируются системой и приходят при закрытом приложении; на
  десктопе — только пока окно запущено (планировщика для закрытого приложения там нет).
- Синхронизация между устройствами не поддерживается. Если она когда-нибудь понадобится, это будет
  новое решение, а не возврат к удалённому: сквозное шифрование на клиенте и сервер, который видит
  только шифротекст.
